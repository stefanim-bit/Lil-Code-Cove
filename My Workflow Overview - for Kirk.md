# My Workflow: Staying Organized with GitHub, Fork & VS Code

*A high-level overview of how I set up and manage my prototype work.*

---

## What I'm working on

I build **interactive HTML prototypes** — practice scenarios that simulate the Wix
editor for training. This means I'm constantly creating files, testing ideas, and
making revisions. Without a system, versions pile up fast and it gets hard to know
which one actually works.

To stay organized (and to edit safely without fear of losing progress), I use three
tools that work together.

---

## The three tools

| Tool | Think of it as… | What I use it for |
|------|-----------------|-------------------|
| **VS Code** | My workshop | Writing and editing the actual code (the HTML prototypes). |
| **GitHub** | The cloud home | An online backup of my whole project that keeps the full history of every change. |
| **Fork** | The control panel | Connects my computer to GitHub. Shows my changes visually and lets me save/send them — no memorizing commands. |

---

## How they work together (my loop)

1. **Edit** a prototype in **VS Code**.
2. **Review** what changed in **Fork** — it highlights every edit so I can see exactly what I did.
3. **Commit** the change in Fork with a short note (a labeled checkpoint, e.g. "Updated Layers panel call mode").
4. **Push** it to **GitHub** so it's backed up with a full history.
5. **Roll back** anytime — if something breaks, I can return to any earlier checkpoint. Nothing good is ever lost.

---

## How I organize the files

- **By Practice Session** (1–4) at the top level, then **by feature** (e.g., Layers, Sub-Pages).
- A separate **Authoring & Code Rule Docs** folder holds my rules, content outlines, and reference screenshots — the "how we do it" lives right next to the work.

---

## In one sentence

> **VS Code** is where I *make* changes, **Fork** is where I *review and save* them,
> and **GitHub** is where they're *backed up with history* — so I can move fast and
> never lose a good version.
